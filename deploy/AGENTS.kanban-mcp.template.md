## Workflow (extremely succinct)

0. **Always pass `board` and `id`** — all board-taking tools require `board` (omitting it is rejected, never defaulted) and the per-ticket tools require `id` too. Capture the `id` from the `ticket_create` response and reuse it verbatim. An `assignee` of `default` is **refused** (`MCP_ALLOW_DEFAULT_ASSIGNEE=true` is the server's opt-out): `default` is the profile the kanban host itself spawns, so a card assigned to it runs THERE — pass your lane's implementer label instead, or omit `assignee` and the ticket stays unassigned (never dispatched).
1. **Orient** — `board_list` first. Then `ticket_list` (status filters; summaries only).
2. **Read** — `ticket_get` for full detail on a ticket you'll touch. **Pass `detail: "full"` whenever you must read a comment verbatim** (a steer, a revision comment, a review verdict): the default `partial` mode **caps comment bodies**, and the clipped tail is usually the payload — the design decision, the requested change, the commit ref. Keep `partial` for scanning and for the ticket's own body/metadata; `kanban_help` reports the current caps.
3. **Claim before work** — `ticket_claim` (`ready → running`). **Identity is set once, at claim**: the tool first ASSIGNS your lane's label (`worker`, else `MCP_CLAIM_WORKER`, else the server default `remote-mcp`) to the card while it is still `ready`, then claims it. That assignment is what the kernel records as the review handoff's implementer, so `ticket_request_review` needs no `worker` argument for a card claimed here — the review handoff inherits it. The label must be **stable per lane** (e.g. `codex-orchestrator`), never per ticket: changing a card's assignee resets the kernel's `consecutive_failures`. It must also **not** be an installed profile — a ready card assigned to one is claimed by the dispatcher within about a minute, so a profile label is refused before any CLI call. The claim TTL is the server's `MCP_CLAIM_TTL_SECONDS` (default 14400s = 4h), passed as an explicit `--ttl`: there is no heartbeat verb in this roster, so the TTL is the whole margin a run gets. If a claim does expire, re-claim before completing — the dispatcher's reclaim books a failed attempt against the ticket. Never edit without claiming.
4. **Track** — `ticket_comment` for decisions/context as you work.
5. **Finish — push, then request review.** Push your branch FIRST, then `ticket_request_review` with a `summary` that is a real handoff: what changed, the repo/branch/sha to verify, and what you already proved (do not make the reviewer re-derive it). The ticket moves to `review`, the dispatcher claims it as a REVIEW run and spawns it on the reviewer profile named on the row (that run force-loads the `sdlc-review` skill), and the verdict comes back to you. **Omit `reviewer`**: the server resolves it (`MCP_REVIEWER_PROFILE`, else the reviewer recorded on the ticket's last changes-requested round), and a lane never needs to know a host profile name — supplying one is an operator override. If you do name one, it must be a Hermes **profile** name, never the skill name: `sdlc-review` is what the run loads, not who it runs as, so passing it is refused outright. **Whichever value ends up on the review row is verified against the installed profile roster and refused if the dispatcher could never spawn it.** When neither you nor the server supplies a reviewer the tool reuses the one recorded on the ticket's last changes-requested round (round 2 of a review); with no source at all the request is refused BEFORE anything is written, because with the flag omitted the kernel keeps whatever assignee the card carries — the stamp has just set it to the lane label — so the row would land on a name the dispatcher never spawns. The reviewer is settled before the implementer stamp, since the stamp moves that same assignee. Moving a `running` ticket also requires `force: true`. The handoff also needs an **implementer label**, and it is usually already there: a card claimed through `ticket_claim` carries the lane label, so `ticket_request_review` inherits it (explicit `worker` > `MCP_CLAIM_WORKER` > the label already on the card) and the stamp is a no-op — pass `worker` only for a card you claimed some other way. That recorded label is what a REQUEST CHANGES verdict routes back on — with none, the reviewer's only exit is a block, so the request is refused. It must **not** be an installed profile (the card returns `ready` carrying it, and the dispatcher spawns a worker for any ready card assigned to an on-disk profile); the lane's control-plane label is the right value.
   - `ticket_complete` finishes with the same review handoff: `review_tier: "LOW"` (or `MCP_COMPLETE_MODE=done`) completes direct to done, while `MEDIUM`/`HIGH` post the completion comment and hand the card to the native review lane (`review`), so `MCP_REVIEWER_PROFILE` must name a profile the dispatcher can spawn **and `MCP_CLAIM_WORKER` must name the lane's implementer label** or the handoff is refused. Do not look for a `review-required` block: that shape has no consumer. Push + record repo/branch/commit either way.
6. **Wait for the verdict — and do not merge before it.** Long-poll `ticket_events` (pass the last seen event id; `kanban_help` has the default and maximum wait) or `ticket_get` until the ticket leaves `review`. `wake_on` defaults to `verdicts`: the kernel's own bookkeeping (heartbeat/claimed/spawned/assigned) and the reviewer's `review → running` claim do NOT wake you — that is the reviewer starting, not news — and `suppressed` counts what the wait swallowed. Use `wake_on: "any"` only when you want the full tail.
   - `done` → **now** merge your branch to main. The reviewer never merges; `done` is what authorises it. Merging before the verdict is a workflow violation — it can delete the very branch the reviewer needs, and a ticket whose branch is gone cannot be reviewed at all.
   - back to `ready` → REQUEST CHANGES → re-claim, fix, push, `ticket_request_review` again.
   - still `blocked` → ESCALATED → surface to the human; do not re-loop.
7. **Blockers** — `ticket_block` with a reason; kinds: `dependency | needs_input | capability | transient`. Never silently stall.

## Rules

- **Never touch the live Hermes install tree** (`~/.hermes`) — work in your repo/worktree.
- **Trust the truncation flags, don't guess.** Every `ticket_get` result reports what it lost: `truncated.body` / `truncated.comments`, a per-comment `truncated` flag, inline `…(N more)` markers, and `comments_total` / `comments_returned` / `comments_dropped`. If any of those is set and you needed the whole thing, re-read with `detail: "full"` — do not reconstruct clipped text, and do not assume an unflagged result was cut.
- **`triage` is not a lane you use.** It is the kernel's internal intake lane for under-specified input: its exit is a specifier that REWRITES the card's title and body, run inside Hermes. `ticket_create` refuses `triage: true`, the bridge never writes there, and there is no agent "later" lane either — if a card is not yours to start, comment why, or block it with `kind: "needs_input"`. `ticket_claim`'s refusal names the lane you are actually in (and there is no promote companion tool): triage has no agent action, `todo` is waiting on the parent ids it lists, `scheduled` is waiting on time, `running`/`review` are held by a claim or a reviewer.
- **Ask before deploy/publish** — block with `ticket_block(reason="approval-required: ...")` and wait for the human.
- **Don't create tickets for yourself** — create follow-ups assigned to the right lane, or comment on the goal.
- Ticket lifecycle details: claims are kernel-enforced (a ticket with an open parent stays `todo`; gates are wired as parents). Full docs: call the MCP server's help tool if present, or see the repo's README/design docs.
